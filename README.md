## 1. Purpose and Overview

This R Markdown report provides a forensic view of two log files generated by a REDCap server running under Apache and PHP on WAMP: the Apache access log and the PHP error log. It is designed to support routine monitoring, security review, and incident investigation by a REDCap system administrator.

The report is structured in eight analytical sections, each building on a common parsed data table. All computations run in a single setup chunk at the top of the file, and the remaining chunks are purely display. This means the report can be re-knitted at any time against a refreshed log file without changing any analysis code.

## 2. Prerequisites

### 2.1 R Packages Required

The setup chunk checks for all required packages and stops with a clear message if any are missing. Install missing packages with `install.packages()` before knitting.

| Package | Description |
|---|---|
| `data.table` | High-performance tabular data operations. Used for all log parsing and aggregation. |
| `tidyverse` | Collection including dplyr, tidyr, purrr, and readr. Used for PHP log processing and cross-log joins. |
| `lubridate` | Date and time parsing and floor/ceiling operations on timestamps. |
| `stringr` | Regex-based string extraction for parsing raw log lines. |
| `DT` | Interactive HTML tables rendered in the knitted report (sortable, searchable, paginated). |
| `ggplot2` | All charts and visualisations in the report. |
| `scales` | Date formatting for time-series axis labels (`date_format` function). |

### 2.2 Log File Paths

Two file paths are set at the top of the setup chunk and must be updated to match your environment:

```r
apache_log_file <- "C:/wamp64/logs/access.log"
php_log_file    <- "C:/wamp64/logs/php_error.log"
```

The Apache path expects the standard WAMP combined log format. The PHP log path is used defensively: if the file does not exist, the PHP sections render empty tables with a warning rather than failing to knit.

> **Note:** If your Apache log is in a different format (e.g. common log format without referrer and user-agent fields), the referrer and user-agent parsing will return `NA`s gracefully, but the User-Agent Analysis section will show empty results.

## 3. Log Parsing and Data Preparation

### 3.1 Apache Log Parsing

The Apache log is read as plain text, one line per row, into a `data.table`. Lines that do not begin with an IP address (IPv4 or the loopback `::1`) are filtered out immediately to discard any header lines or blank rows.

Each line is then parsed using a combination of `tstrsplit` (splitting on spaces) and `str_extract` (targeted regex extraction). The key fields extracted are:

| Field | Description |
|---|---|
| `ip` | Client IP address. First space-delimited token. |
| `time` | Request timestamp. Extracted by regex matching the Apache date format `dd/Mon/yyyy:HH:MM:SS +zzzz`, then parsed to POSIXct in UTC. |
| `request` | Full HTTP request string extracted from the first quoted field, e.g. `GET /redcap/index.php HTTP/1.1`. |
| `method` | HTTP method (GET, POST, etc). First token of the request string. |
| `uri` | Requested path including query string. Middle token of the request string. |
| `protocol` | HTTP protocol version. Last token of the request string. |
| `status` | HTTP response status code as integer (200, 404, 500, etc). |
| `bytes` | Response body size in bytes. Second number after the status code. May be `NA` if your log format uses a dash for missing values. |
| `user_agent` | Browser or tool identifier string. Extracted from the last quoted field in combined log format. |
| `referrer` | Referring URL. Extracted as the second quoted field using `vapply` for type safety. |

### 3.2 Derived Columns

Several additional columns are computed from the parsed fields and reused across multiple report sections:

| Column | Description |
|---|---|
| `req_hour` | Timestamp floored to the nearest hour. Used for time-series charts and cross-log correlation. |
| `req_minute` | Timestamp floored to the nearest minute. Used for per-minute request rate analysis. |
| `dow` | Day of week as a three-letter abbreviation (Mon, Tue, etc). Stored as character to avoid `data.table` type conflicts with `lubridate` factors. |
| `req_hour_of_day` | Integer hour of day (0–23). Used as the x-axis of the day/hour heatmap. |
| `status_cat` | Status code grouped into five categories: `2xx Success`, `3xx Redirect`, `4xx Client Error`, `5xx Server Error`, `Other`. Used for stacked area chart and byte size analysis. |
| `uri_stem` | URI with query string and fragment stripped (everything before `?` or `#`). Used for endpoint profiling and login detection. |
| `uri_length` | Character count of the raw URI. Long URIs are flagged as potential injection payloads. |
| `ua_category` | User-agent classified into four categories: `Browser`, `Bot/Tool/Scanner`, `Empty/Missing`, `Unknown/Custom`. |

### 3.3 PHP Log Parsing

The PHP log is parsed using a single regex pattern that matches the standard PHP error log format:

```
[dd-Mon-yyyy HH:MM:SS UTC] PHP <Type>: <Message>
```

The pattern captures three groups: the datetime string, the error type (Warning, Fatal error, Notice, etc), and the full message text. The datetime is parsed with `lubridate` using two format orders to handle logs with and without the UTC timezone token.

If the file does not exist, or if the pattern matches no lines, empty data frames are created and the PHP sections render gracefully with no crash. A warning is printed to the R console in either case.

## 4. Report Sections Explained

### 4.1 Traffic Overview

**Apache Log: Latest 20 Entries** — A raw table of the 20 most recent log entries, sorted by timestamp descending. Useful for a quick sanity check that the log was read correctly and to confirm the time range of the data.

**Requests per Hour** — A line chart of total request volume aggregated by hour. This is your primary traffic baseline. Look for the normal working-hours peak pattern for your institution, and treat deviations as investigation triggers. A sharp spike outside business hours on a REDCap server with no scheduled surveys is unusual.

**Day-of-Week / Hour-of-Day Heatmap** — A tile heatmap where each cell represents the total request count for a given combination of weekday and hour. Darker blue means more traffic. This chart is most useful for establishing what normal looks like over a multi-day or multi-week log window. Anomalous cells (unusually dark at 3am Sunday, for example) stand out immediately.

**Status Code Distribution Over Time** — A stacked area chart showing how the mix of 2xx, 3xx, 4xx, and 5xx responses changes per hour. A growing red band (5xx) often precedes or coincides with PHP fatal error spikes and is the clearest visual signal that something is wrong server-side.

### 4.2 Endpoint & URI Analysis

**Top URI Stems (with Error Rates)** — Every unique URI path (query strings stripped) ranked by hit count, with the percentage of requests returning 2xx, 4xx, and 5xx responses, plus the count of unique source IPs. A URI with a high `pct_5xx` is generating server errors and deserves immediate attention. A URI that appears in this table but that you do not recognise as a legitimate REDCap path is a red flag.

**Low-Hit URIs Always Returning 200** — URIs with five or fewer total hits that returned 200 on every attempt. Legitimate users tend to generate many requests to the same endpoints; a URI that appears only once or twice but always succeeds may indicate targeted, quiet probing of a specific resource. This is a soft signal rather than a definitive alert.

**Long URIs (>200 characters)** — Requests with URIs longer than 200 characters. SQLi attempts, path traversal strings, and encoded shellcode all produce unusually long URI strings. This table shows the top 50 longest, ordered by length, with the associated IP and response status.

**URI Length Distribution** — A histogram of all URI lengths. The distribution for a healthy REDCap server is right-skewed with a peak below 100 characters. A secondary bump or long tail above 200 characters indicates scanning or injection activity.

### 4.3 REDCap-Specific Monitoring

**REDCap Endpoint Activity** — Requests filtered to REDCap-specific path patterns: `/api/`, `redcap_v` (versioned REDCap directories), `esignature`, `surveys/`, `DataEntry`, `record_home`, and File Repository. This narrows the endpoint table to the paths that matter most for a REDCap installation. High error rates on `/api/` or `DataEntry` are particularly worth investigating.

**API Endpoint Access by IP** — A breakdown of which IP addresses are hitting the REDCap API endpoint, how many times, and which HTTP methods they are using. The REDCap API should only be accessed by known integration systems and approved token holders. Any unexpected IP or the use of methods other than POST against the API endpoint is a red flag.

**Login POST Activity** — A summary of IPs sending POST requests to `index.php`, which is the REDCap login endpoint. The table shows total POST count, how many distinct minutes the activity spanned, and the first and last timestamps. A high `post_count` combined with a low `minutes_active` value suggests rapid automated attempts. The rapid login flag table beneath it highlights any IP that exceeded ten POSTs in a single minute, which is the threshold used here for credential stuffing.

### 4.4 Security Forensics

This section contains the core investigative queries and is the closest to a traditional security audit output.

| Finding | Description |
|---|---|
| Install Script Hits | Any request to a URI matching `install.php`. REDCap's installer should never be accessible after initial setup. Any hit here is a high-priority finding. |
| Client Errors (4xx) by IP | IP addresses ranked by total 4xx response count. A high 4xx count from a single IP often indicates scanning or authentication probing. |
| Server Errors (5xx) by IP | IP addresses ranked by total 5xx response count. An IP consistently triggering server errors may be sending malformed requests or exploiting a specific endpoint. |
| Unusual HTTP Methods | Any method other than GET or POST. OPTIONS and HEAD are common from scanners; PUT, DELETE, TRACE, and CONNECT are rarely legitimate against a REDCap server. |
| Suspicious URIs | URIs matching a regex pattern covering common SQLi keywords (`union`, `select`, `sleep`, `benchmark`), path traversal (`../`), and command injection markers (`cmd=`, `exec=`). Case-insensitive. |
| High Request Rate | IP and minute combinations with more than 50 requests in a single minute. This is the automated scanning threshold used in this report. |

### 4.5 User-Agent Analysis

User-agents are classified into four categories using regex matching: `Browser` (all common browser families), `Bot/Tool/Scanner` (known crawlers, wget, curl, Python requests, and similar tools), `Empty/Missing` (requests with no user-agent or a literal dash), and `Unknown/Custom` (anything that does not match the other categories).

The bar chart gives a quick proportional view. The detail table beneath it lists the top 20 specific user-agent strings in the `Bot/Tool/Scanner` category. Review this list for anything unexpected: legitimate search engine bots are normal, but vulnerability scanners (Nikto, sqlmap, Acunetix, etc) or your own IP appearing with a `curl` user-agent outside of a known task are worth noting.

### 4.6 Byte Size Analysis

This section only renders if the `bytes` field is present in your log (some Apache configurations log a dash instead of a byte count for certain request types). If available, three sub-analyses are shown:

- Median and max response size by status category. This establishes what a normal response looks like for each status type on your server.
- Large responses (top 1% by byte count). Unexpectedly large responses on sensitive endpoints could indicate data being returned that should not be, or a misconfigured endpoint returning full database dumps on error.
- Small 200 responses (under 50 bytes). A 200 OK with almost no body can indicate a silent authentication failure where the server returns success but sends no meaningful content.

### 4.7 PHP Error Analysis

Three views of the PHP error log are provided:

- **Error type counts** — A frequency table of Warning, Fatal error, Notice, Deprecated, and other PHP error types. A sudden increase in Fatal errors often correlates with a server-side problem triggered by a specific request.
- **Top error messages** — The five most frequent full error message strings. Recurring messages point to a persistent code issue, often in an external module.
- **Errors over time** — A line chart of error counts per hour broken down by type. This is the PHP-side equivalent of the status code chart and is designed to be read alongside it.
- **PHP files generating errors** — The PHP source files most frequently mentioned in error messages. This quickly identifies which module or REDCap component is the source of recurring errors.

### 4.8 Cross-Log Correlation

The final section joins the Apache and PHP logs on the `req_hour` timestamp, producing a unified view of hours where both Apache 5xx errors and PHP errors were recorded. The line chart overlays both series so that aligned spikes are immediately visible.

Hours where both `apache_5xx` and `php_errors` are greater than zero in the accompanying table are the most actionable: they represent moments where a specific request triggered a server-side failure that was also logged by PHP. These are the rows to start from when investigating an incident.

## 5. Known Limitations

- **Log rotation** — The report reads a single log file. If Apache rotates logs nightly, you will only see the current file. Point `apache_log_file` at an unrotated or concatenated file for longer-range analysis.
- **Log format assumption** — The parser assumes Apache combined log format. Common log format (without referrer and user-agent) will parse correctly for the core fields but will return `NA`s for referrer and user-agent columns.
- **Time zone** — All timestamps are parsed and stored in UTC. If your server logs in local time, adjust the `tz` argument in the `as.POSIXct` call.
- **Byte field availability** — The `bytes` field is parsed from the position immediately after the status code. If your log format places additional fields between them, the regex will fail silently and `bytes` will be `NA`.
- **REDCap endpoint patterns** — The regex patterns for REDCap-specific URIs are written for standard REDCap installations. If your REDCap is installed under a non-standard path, update the pattern strings in the setup chunk.
- **PHP log encoding** — The PHP log is read with `encoding = UTF-8`. If your server writes logs in a different encoding, non-ASCII characters in error messages may appear as escaped hex sequences.
- **Credential stuffing threshold** — The 10 POSTs per minute threshold for rapid login flagging is a starting point. Adjust the `N > 10` filter to suit your server's normal behaviour.

## 6. Future Enhancements

### Enhancement 1: Date Range Filter at the Top of the Report

Currently the report processes the entire log file on every knit. Adding two parameters at the top of the setup chunk would allow the analyst to restrict all queries and charts to a specific date window without modifying any downstream code.

```r
filter_start <- as.POSIXct('2026-01-01 00:00:00', tz='UTC')
filter_end   <- as.POSIXct('2026-01-31 23:59:59', tz='UTC')
log <- log[time >= filter_start & time <= filter_end]
```

Because all downstream objects are derived from `log`, every table and chart in the report will automatically reflect the filtered window. Setting both values to `NA` (with an `is.na` guard on the filter line) would restore full-file behaviour. This is the highest-value enhancement because it turns the report from a whole-log dump into a targeted investigation tool.

### Enhancement 2: IP Allowlist / Blocklist Annotation

Many of the security tables (client errors, suspicious URIs, high request rate) would be more actionable if known IPs were annotated inline. Maintain a small CSV file with two columns (`ip` and `label`), load it in the setup chunk, and left-join it onto any table where IP appears before rendering. Rows without a match get an empty label; rows with a match show the label in a new column. This turns a table of anonymous IPs into one where your own systems are already identified and can be visually distinguished from external traffic.

### Enhancement 3: Automated Summary / Executive Block

A short summary block at the very top of the rendered HTML, computed in the setup chunk, would surface the most important numbers immediately: total requests in the log window, count of 5xx errors, count of suspicious URI hits, any `install.php` access, and the top flagged IP. The R Markdown inline code syntax makes this straightforward without requiring a separate chunk. This is particularly useful if the report is being shared with a manager or IT security team who need a one-paragraph read before diving into the detail.

### Enhancement 4: Apache Error Log Integration

This report currently reads the Apache access log and the PHP error log. Apache also writes a separate error log (typically `error.log` in WAMP) that captures server-side errors at the Apache layer, before PHP is even invoked — including permission denied errors, failed module loads, and SSL handshake failures. Adding a third file path variable (`apache_error_log_file`) and a parser modelled on the PHP parser would open up detection of things like mod_security blocks and failed authentication at the Apache layer rather than the application layer.

### Enhancement 5: Scheduled / Automated Delivery

Currently the report is produced manually by opening RStudio and knitting the file. For a production monitoring workflow, the report should be generated automatically on a schedule and either saved to a known location or emailed to the administrator. Create a small wrapper R script that calls `rmarkdown::render()` with an output file name that includes the current date, then schedule it using Windows Task Scheduler. The `blastula` or `sendmailR` package can attach or inline the resulting HTML report in an email. Combined with Enhancement 1, the scheduled script can automatically set `filter_start` to 24 or 168 hours before the run time so each report covers exactly the period since the last one.
